# 결정 기록

## DEC-001: 지원 리그는 K1과 J1

- 상태: 채택
- 결정: API-Football K1=`292`, J1=`98`을 같은 fixtures 응답에서 제공한다.
- 이유: 사용자는 두 리그의 예정 경기와 순위를 하나의 제품 흐름에서 비교한다.

## DEC-002: 공식 순위는 리그별로 분리

- 상태: 채택
- 결정: `standingsByLeague`에 K1/J1 공식 standings를 분리해 반환한다.
- 이유: 서로 다른 리그의 rank와 team ID를 섞지 않고 부분 공급자 실패도 표현할 수 있다.

## DEC-003: 일정 범위와 캐시

- 상태: 채택
- 결정: 한국시간 오늘부터 14일을 조회하고 fixtures는 10분 캐시한다.
- 이유: API 호출량을 제한하면서 가까운 일정의 최신성을 유지한다.

## DEC-004: 사전 배당은 선택 기반 읽기 전용

- 상태: 채택
- 결정: `/api/pre-match-odds?fixture={id}`는 선택한 경기에서만 GET으로 호출하고 30분 캐시한다.
- 이유: 공급 범위가 불완전하므로 불필요한 전체 목록 호출을 피한다. 빈 bookmaker 목록은 정상이다.

## DEC-005: Betman 매칭은 보수적으로

- 상태: 채택
- 결정: 리그·날짜·홈/원정 팀 ID·시작시간 15분 이내가 모두 맞는 단일 후보만 연결한다.
- 이유: 잘못된 배당 연결이 배당 없음보다 위험하다.

## DEC-006: 별칭은 확인된 팀 ID와 표기만 등록

- 상태: 채택
- 결정: 팀 별칭은 리그별 API-Football 팀 ID에 연결하고, 확인된 실제 표기만 추가한다.
- 이유: 동명 팀과 불확실한 음역으로 인한 오매칭을 막는다.

## DEC-007: 회귀 하네스는 GET만 사용

- 상태: 채택
- 결정: 하네스는 PUT/POST/DELETE를 호출하지 않는다.
- 이유: 운영 데이터와 사용자가 설정한 Betman 회차를 변경하지 않는 검증이 필요하다.

## DEC-008: 시즌 키는 리그별 규칙으로 계산

- 상태: 채택
- 결정: K1은 달력 연도, J1은 7월~다음 해 6월의 종료 연도를 API 시즌 키로 사용하고 응답의 각 리그 메타에 해당 `season`을 제공한다.
- 이유: 2026-27 J1의 실제 API 키는 `2027`이며 하나의 공통 시즌 값은 잘못된 일정과 전환 대회 순위를 조회한다.

## DEC-009: 경기 상세는 명시적 선택 기반 작업공간으로 연다

- 상태: 채택
- 날짜: 2026-08-13
- 결정: 첫 fixtures 응답에서는 예정 경기 목록만 표시하고 첫 경기를 자동 선택하지 않는다. 사용자가 경기를 선택한 뒤에만 Predictions와 pre-match odds를 조회한다. 넓은 화면에서는 목록과 상세를 독립 스크롤 가능한 두 열로 표시하고, 1050px 이하에서는 상세가 목록을 대체하며 닫기 버튼으로 복귀한다.
- 이유: 의도하지 않은 상세 API 요청을 피하고, 목록 탐색과 상세 분석을 화면 크기에 맞게 분리한다.

## DEC-010: 사전 배당은 모든 bookmaker의 Match Winner를 동시에 표시

- 상태: 채택
- 날짜: 2026-08-13
- 결정: bookmaker 선택상자를 두지 않고 API 응답의 모든 bookmaker를 응답 순서대로 표시한다. 각 업체는 완전한 Match Winner의 Home / Draw / Away만 소수 둘째 자리까지 표시하며, 세 값 중 하나라도 없으면 `미제공`으로 표시한다.
- 이유: 제공자별 가용성을 한 번에 비교하게 하면서 불완전한 1X2 데이터를 완전한 배당처럼 보이지 않게 한다.

## DEC-011: 맞대결은 상세 선택 후 지연 조회

- 상태: 채택
- 날짜: 2026-08-14
- 결정: 경기 목록에서는 맞대결을 조회하지 않고, 상세경기를 선택한 경우에만 해당 팀 조합을 한 번 조회해 30분 캐시한다. rate-limit 오류는 자동 재시도하지 않는다.
- 이유: 한 번의 목록 조회가 예정 경기 수만큼 공급자 요청을 만드는 fan-out과 시간당 요청 제한 초과를 제거한다.

## DEC-012: 과거 Betman 팀명 변형은 명시적으로 등록하고 로컬 재매칭

- 상태: 채택
- 날짜: 2026-08-22
- 결정: 과거 마감게임에서 실제 확인한 띄어쓰기·붙여쓰기 변형만 리그별 팀 별칭에 추가한다. 확정된 `TEAM_MATCH_FAILED` 행은 Betman을 다시 요청하거나 원천 행을 삭제하지 않고 현재 별칭 레지스트리로 로컬 재매칭한다.
- 이유: 일반적인 공백 제거 또는 유사도 매칭은 다른 팀의 오연결 위험이 있다. 명시적 별칭과 로컬 재매칭은 확정 원천 데이터의 불변성을 유지하면서 확인된 누락만 복구한다.

## DEC-013: 저장된경기 선택은 원본 예측과 분리된 단일 메타데이터

- 상태: 채택
- 날짜: 2026-08-27
- 결정: 각 저장 행은 선택지 하나 또는 선택 없음만 유지하며 `selected_option_index`에 별도 저장한다. 선택 저장은 확률·배당·기대수익·저장일시를 갱신하지 않는다.
- 이유: 사용자의 표시·분류 의도를 영속화하면서 기존 분석 입력과 최신순 정렬의 의미를 보존한다.

## DEC-014: 자체 승부예측 Phase 2를 폐기하고 외부 Predictions만 유지

- 상태: 채택
- 날짜: 2026-09-03
- 결정: API-Football Predictions는 외부 참고정보로 유지한다. 자체 승부예측 모델, 자동 확률 산출, 모델 학습, 확률 보정과 백테스트는 제품 범위에서 제외한다. 사용자가 입력한 확률과 선택 표시는 사용자 판단 기록으로 취급한다.
- 이유: 현재 제품의 핵심은 실제 경기·배당·결과 조회와 판단 기록이다. 자체 예측은 검증 데이터와 운영 복잡도를 크게 늘리며 배포 안정성, 접근통제와 데이터 품질보다 우선하지 않는다.

## DEC-015: API-Football 정상 응답은 D1 공유 캐시로 관리

- 상태: 채택
- 날짜: 2026-09-03
- 결정: fixtures, Predictions, 사전 배당, 맞대결의 프로세스 메모리 캐시를 D1 공유 캐시로 교체한다. 동일 키 갱신은 Worker 내부 in-flight 병합과 D1 15초 임대로 한 번만 수행하고, 오류와 fixtures 부분 성공은 저장하지 않는다. 갱신 장애 시 제한된 기간의 마지막 정상값을 사용한다.
- 이유: 로컬 단일 프로세스와 달리 웹 배포의 여러 Worker 인스턴스는 메모리 캐시를 공유하지 않아 같은 화면 요청이 API-Football 중복 호출과 rate-limit 오류를 만들 수 있다. 공유 정상값과 원자적 갱신 소유권이 환경 차이를 제거한다.
