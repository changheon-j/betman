# 기능 단위 세션 관리 설계

작성일: 2026-08-20
상태: 승인됨

## 1. 목적

Betting Analysis System의 기능 개선 작업을 리딩, 설계, 개발, 테스트 단계로 분리한다. 현재 Codex 작업은 프로젝트 리딩과 사용자 승인 전용으로 유지하고, 기능별 작업은 단계적으로 생성한다. 작업 결과는 Git 브랜치와 저장소 문서에 연결해 채팅 목록이 바뀌거나 작업이 보관된 뒤에도 추적할 수 있게 한다.

이 설계의 목표는 다음과 같다.

- 요구사항 결정과 구현 권한을 분리한다.
- 승인되지 않은 설계가 개발로 넘어가지 않게 한다.
- 개발자 역할과 테스트 역할을 분리한다.
- 좌측 작업 목록에는 현재 진행 중인 작업만 남긴다.
- 보관된 작업을 안정적으로 찾고 다시 열 수 있게 한다.
- 현재 `main`과 기존 미커밋 변경을 기능 작업으로부터 보호한다.

## 2. 기본 원칙

- 현재 작업은 프로젝트 리딩·오더·승인 전용 작업이다.
- 활성 기능은 초기 운영에서 한 번에 하나만 허용한다.
- 설계, 개발, 테스트 작업은 한꺼번에 만들지 않고 승인 단계에 따라 순차 생성한다.
- 기능마다 전용 Git 브랜치와 worktree를 사용한다.
- 설계, 개발, 테스트는 같은 기능 ID와 같은 기능 브랜치를 공유한다.
- 테스트 작업은 코드나 문서를 수정하지 않는 읽기 전용 검증 역할이다.
- 테스트 실패는 개발 작업으로 회송하고 같은 테스트 작업에서 재검증한다.
- 테스트 통과만으로 병합하거나 보관하지 않는다. 사용자의 최종 승인이 필요하다.
- 작업 목록의 기준 정보는 저장소의 세션 등록부다.

## 3. 역할과 권한

### 3.1 리딩 작업

작업명은 `[리딩] Betting Analysis System`으로 유지한다. 이 작업은 다음 권한을 가진다.

- 기능 요청 접수와 범위 조정
- 기능 ID 발급
- 우선순위와 활성 기능 결정
- 설계 작업 생성과 설계 승인
- 개발 작업 생성과 구현 승인
- 테스트 작업 생성과 결함 회송
- 최종 승인 확인
- 세션 등록부와 테스트 보고서 갱신
- 브랜치 반영 방식 결정
- 완료 작업 보관 및 보관 해제

리딩 작업에서는 기능 구현 코드를 직접 수정하지 않는다. 세션 관리 문서와 승인 기록만 관리한다.

### 3.2 설계 작업

설계 작업은 승인된 기능 요청 하나만 다룬다.

- 요구사항과 비목표 명시
- 현재 코드와 데이터 계약 조사
- 대안과 트레이드오프 비교
- 설계 문서 작성
- 구현 계획 작성
- 테스트 가능한 완료 조건 정의

설계 작업은 제품 코드를 수정하지 않는다. 설계 결과는 리딩 작업에 보고하며, 사용자 승인 전에는 개발 작업을 만들지 않는다.

### 3.3 개발 작업

개발 작업은 승인된 설계와 구현 계획만 실행한다.

- 테스트 우선 개발
- 기능 브랜치 내 코드·테스트·필요 문서 변경
- 단계별 커밋
- 타입 검사, 린트, 빌드, 단위 테스트 실행
- 변경 파일, 커밋, 검증 결과, 알려진 제한사항 보고

설계와 다른 구현이 필요하면 임의로 범위를 바꾸지 않고 리딩 작업에 변경 승인을 요청한다.

### 3.4 테스트 작업

테스트 작업은 개발 작업과 분리된 읽기 전용 검증 역할이다.

- 승인된 완료 조건과 변경 diff 검토
- 정적 검사, 단위 테스트, 통합 테스트, 화면 검증 수행
- 통과·실패 수와 명령 기록
- 재현 가능한 결함 보고
- 최종 판정: `통과`, `수정 필요`, `검증 불가`

테스트 작업은 결함을 직접 수정하지 않는다. `수정 필요`이면 리딩 작업이 개발 작업에 회송하고, 수정 완료 후 같은 테스트 작업에서 다시 검증한다.

## 4. 기능 식별과 명명

기능에는 순차적인 고유 ID를 부여한다.

```text
F-001, F-002, F-003, ...
```

작업 이름은 다음 형식을 사용한다.

```text
[리딩] Betting Analysis System
[설계][F-001] 기능명
[개발][F-001] 기능명
[테스트][F-001] 기능명
```

브랜치는 다음 형식을 사용한다.

```text
codex/f-001-짧은-기능명
```

설계서, 구현 계획, 테스트 보고서와 세션 등록부는 같은 기능 ID를 사용한다. 기능 ID는 완료나 보관 뒤에도 재사용하지 않는다.

## 5. 단계별 작업 생성

기능 작업은 다음 순서로 하나씩 생성한다.

1. 리딩 작업에서 기능 요청과 성공 기준을 확정한다.
2. 기능 ID를 발급하고 세션 등록부 상태를 `요청`으로 기록한다.
3. 전용 브랜치와 worktree에서 설계 작업만 생성한다.
4. 설계서와 구현 계획을 사용자가 승인하면 상태를 `설계 승인`으로 바꾼다.
5. 같은 기능 브랜치와 worktree를 사용하는 개발 작업을 생성한다.
6. 개발 결과가 준비되면 테스트 작업을 생성한다.
7. 테스트 실패 시 개발 작업으로 회송하고 재검증한다.
8. 테스트 통과 후 사용자가 최종 승인한다.
9. 브랜치를 승인된 방식으로 반영하고 기록을 갱신한다.
10. 설계·개발·테스트 작업을 보관한다.

설계 단계에서 기능이 취소되면 개발·테스트 작업을 만들지 않는다.

## 6. Git과 worktree 정책

- 기능마다 전용 `codex/` 브랜치와 worktree 하나를 만든다.
- 설계, 개발, 테스트 작업은 같은 기능 worktree를 이어서 사용한다.
- 단계가 순차적이므로 같은 worktree에서 동시 편집하지 않는다.
- 테스트 단계에서는 파일을 수정하거나 커밋하지 않는다.
- `main`에는 사용자 최종 승인 전 변경을 반영하지 않는다.
- 기존 작업 트리의 미커밋 파일은 기능 worktree로 임의 이동하거나 덮어쓰지 않는다.
- 기능 종료 시 브랜치 병합, PR, 유지 또는 폐기는 리딩 작업에서 사용자에게 확인한다.

긴급 수정은 일반 기능과 구분해 `HOTFIX-001` 형식의 별도 ID와 브랜치를 사용할 수 있다. 긴급 수정도 개발·테스트·최종 승인 절차를 생략하지 않는다.

## 7. 세션 등록부

저장소 루트 문서 영역에 `docs/SESSION-REGISTRY.md`를 둔다. 등록부는 리딩 작업만 수정한다.

기능 항목은 최소 다음 정보를 포함한다.

| 필드 | 설명 |
|---|---|
| 기능 ID | 중복되지 않는 `F-###` 식별자 |
| 기능명 | 사용자가 이해할 수 있는 짧은 이름 |
| 상태 | 현재 단계 |
| 우선순위 | 대기 기능의 실행 순서 |
| 브랜치 | 기능 전용 Git 브랜치 |
| worktree | 기능 작업 경로 또는 식별 정보 |
| 설계 작업 | 제목과 작업 ID |
| 개발 작업 | 제목과 작업 ID |
| 테스트 작업 | 제목과 작업 ID |
| 설계서 | 저장소 내 문서 경로 |
| 구현 계획 | 저장소 내 문서 경로 |
| 테스트 보고서 | 저장소 내 문서 경로 |
| 최신 결과 | 마지막 단계의 짧은 요약 |
| 남은 문제 | 차단 사항 또는 후속 행동 |
| 생성일·완료일·보관일 | 수명주기 날짜 |

허용 상태는 다음과 같다.

```text
요청
설계 중
설계 승인
개발 중
테스트 중
수정 필요
최종 승인
보관
취소
```

상태 변경은 리딩 작업에서만 수행한다. 각 역할 작업은 결과를 리딩 작업에 보고하고 등록부를 직접 수정하지 않는다.

## 8. 인수인계 산출물

### 설계에서 개발로

- 승인된 설계서
- 구현 계획
- 명시적인 범위와 비목표
- 수정 예상 파일
- 완료 조건과 필수 테스트
- 알려진 제약과 미결정 사항 없음

### 개발에서 테스트로

- 변경 파일 목록
- 커밋 목록
- 구현 요약
- 실행한 검증 명령과 결과
- 미실행 검증과 이유
- 알려진 제한사항

### 테스트에서 리딩으로

- 검사한 브랜치와 커밋 SHA
- 실행 환경
- 실행한 명령
- 통과·실패·건너뜀 수
- 화면 또는 API 검증 증거
- 발견 결함과 재현 절차
- 최종 판정

테스트 작업은 결과를 채팅으로 보고한다. 리딩 작업은 이를 `docs/session-reports/F-###-test.md`에 저장하고 등록부에 연결한다.

## 9. 실패와 회송 처리

- 설계가 불충분하면 설계 작업을 계속 사용해 수정한다.
- 개발 중 설계 변경이 필요하면 작업을 멈추고 리딩 승인을 요청한다.
- 테스트가 실패하면 상태를 `수정 필요`로 바꾸고 개발 작업에 결함과 재현 절차를 전달한다.
- 개발 작업은 결함 수정과 회귀 테스트를 완료한 뒤 다시 보고한다.
- 테스트 작업은 수정된 커밋을 대상으로 전체 필수 검증을 다시 실행한다.
- 외부 API, 권한, 네트워크 등으로 검증할 수 없으면 `검증 불가`로 보고하고 사용자가 처리 방향을 결정한다.

## 10. 보관과 복원

- 보관은 삭제가 아니며 작업 기록을 유지한다.
- 테스트 통과와 사용자 최종 승인, 등록부·보고서 갱신이 모두 끝난 뒤 보관한다.
- 설계·개발·테스트 작업을 함께 보관하고 리딩 작업은 활성·고정 상태로 유지한다.
- 보관된 작업은 등록부의 작업 ID로 찾는다.
- 사용자가 과거 작업을 요청하면 리딩 작업이 해당 작업을 열거나 보관 해제한다.
- 완료 기능에 추가 변경이 필요하면 기존 작업을 장기 재사용하지 않고 새 기능 또는 수정 주기를 등록해 문맥을 분리한다.

현재 OpenAI 공식 문서에서 보관된 Codex 작업의 고정된 UI 메뉴 경로는 확인되지 않았으므로, 보관 작업 검색은 UI 위치보다 세션 등록부와 작업 ID를 기준으로 한다.

## 11. 동시 진행 정책

초기 운영에서는 활성 기능을 하나로 제한한다. 여러 요청은 등록부의 대기 목록에 기록하고 우선순위에 따라 처리한다.

동시 진행은 다음 조건을 모두 만족하는 경우에만 향후 허용할 수 있다.

- 기능별 수정 파일이 겹치지 않는다.
- 독립된 브랜치와 worktree를 사용한다.
- 리딩 작업이 각 기능의 현재 테스트 대상 커밋을 구분할 수 있다.
- 사용자가 동시 진행을 명시적으로 승인한다.

## 12. 완료 조건

세션 관리 도입은 다음 조건을 만족할 때 완료된다.

- 현재 작업 이름이 `[리딩] Betting Analysis System`으로 설정된다.
- 현재 작업이 좌측 목록에 고정된다.
- `docs/SESSION-REGISTRY.md` 초기 등록부가 존재한다.
- 기능 요청, 단계 승인, 결과 보고, 회송, 보관 규칙이 저장소 문서에 기록된다.
- 첫 기능에 `F-001`을 부여하고 설계 작업을 단계적으로 생성할 수 있다.
- 완료된 작업을 등록부의 작업 ID로 찾아 열거나 보관 해제할 수 있다.
- 설계·개발·테스트 작업이 사용자 최종 승인 전 자동 병합 또는 자동 보관되지 않는다.

## 13. 제외 범위

- 여러 기능의 기본 병렬 개발
- 테스트 작업의 코드 자동 수정
- 사용자 승인 없는 자동 병합·푸시·보관
- 보관된 모든 과거 작업의 소급 등록
- 외부 프로젝트 관리 서비스 도입
- 작업 상태를 주기적으로 변경하는 자동화
