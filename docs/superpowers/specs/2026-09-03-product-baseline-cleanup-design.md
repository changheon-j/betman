# 제품 기준선 및 배포 전 정리 설계

작성일: 2026-09-03

## 1. 목적

현재 Betting Analysis System의 실제 구현을 제품 기준선으로 다시 정의하고, 초기 샘플 구상과 현재 결과물의 차이를 문서화한다. 배포 전에 불필요한 개발 로그와 오래된 미래 계획을 정리하되, 완료된 설계서·구현 계획·테스트 근거는 역사 기록으로 보존한다.

이번 정리는 제품 기능을 새로 추가하거나 삭제하는 작업이 아니다. 현재 제공 중인 API-Football Predictions 화면과 API는 유지한다. 폐기 대상은 향후 자체 승부예측 모델, 자동 확률 산출, 모델 학습, 확률 보정 및 백테스트 계획이다.

## 2. 현행 제품 기준선

제품은 다음과 같이 정의한다.

> K1·J1 실제 경기 정보와 공개 배당을 조회하고, Betman 마감 배당·경기 결과 및 사용자의 판단 기록을 보존하는 개인용 분석 도구

### 핵심 기능

- API-Football 기반 K1·J1 실제 일정, 순위, 최근 경기와 맞대결
- API-Football 사전 배당과 Predictions 참고 정보
- Betman 현재 회차 배당 연결
- Betman 마감 경기 결과와 최종 배당의 D1 아카이브
- 사용자가 입력한 확률·기대수익 및 선택 표시의 D1 저장

### 명시적 비목표

- 자체 승부예측 모델과 자동 추천
- 모델 학습 및 자동 확률 산출
- 확률 보정과 백테스트
- 자동 베팅, 베팅 권유 또는 수익 보장
- PWA 오프라인 기능

API-Football Predictions는 외부 공급자가 제공하는 참고 정보다. 애플리케이션이 자체적으로 생성하는 승부예측과 구분하며 현재 화면과 API를 유지한다. 사용자가 입력하는 확률과 선택 표시는 추천 결과가 아니라 사용자의 판단 기록이다.

## 3. 초기 구상과 현재 결과물의 차이

초기 저장소는 Vinext 전체 스택 starter에서 출발했다. 최초 화면은 정적 K리그1 샘플 일정·순위·관심 경기와 데모 상세정보를 표시하는 경기 안내 화면이었다.

현재 제품은 다음 단계를 거쳐 실제 데이터 중심의 분석·기록 도구로 변화했다.

1. 정적 K리그1 샘플 화면에서 K1 실제 일정·순위 조회로 전환했다.
2. J1과 리그별 시즌 해석을 추가했다.
3. 명시적으로 선택한 경기의 상세 분석, 최근 경기, 맞대결, API-Football Predictions 및 사전 배당을 추가했다.
4. 사용자가 지정한 Betman 현재 회차 배당을 실제 경기와 안전하게 연결했다.
5. Betman 마감게임의 K1·J1 경기 결과와 최종 배당을 D1에 영구 보존하는 배당기록을 구축했다.
6. 사용자의 확률·기대수익 저장에 더해 선택 1~3 중 하나를 판단 표시로 영속하는 저장된경기 흐름을 완성했다.
7. 제품의 중심은 관심 경기 안내에서 실제 배당·결과 조회와 사용자 판단 기록으로 이동했다.

자체 승부예측 Phase 2는 현재 제품 목적에 필수적이지 않고 데이터 모델·검증·운영 복잡도를 크게 늘리므로 폐기한다. 향후 작업은 예측 모델보다 배포 안정성, 접근통제, 데이터 품질과 운영 가시성을 우선한다.

## 4. 문서 구조

활성 문서는 현재 제품의 단일 기준으로 유지한다.

- `README.md`: 현재 기능과 실행·검증 방법 요약
- `docs/PRODUCT.md`: 현행 목적, 사용자 흐름, 화면 규칙과 비목표
- `docs/PRODUCT-EVOLUTION.md`: 초기 구상부터 현재 제품까지의 변화와 범위 결정
- `docs/ROADMAP.md`: 배포와 운영에 필요한 가까운 작업만 기록
- `docs/HANDOFF.md`: 현재 작업 상태, 주의사항과 다음 실행 순서
- `docs/DECISIONS.md`: 자체 승부예측 Phase 2 폐기 결정 기록

`docs/superpowers/specs`와 `docs/superpowers/plans`의 완료 문서는 원문 그대로 보존한다. 이는 현재 요구사항이 아니라 결정 당시의 설계·구현 근거다. 활성 문서가 이를 현재 계획처럼 인용하지 않도록 구분한다.

## 5. 개발 로그 정리

다음 Git 미추적 개발 서버 로그만 삭제한다.

- `.codex-dev-server.err.log`
- `.codex-dev-server.out.log`
- `.codex-devserver.err.log`
- `.codex-devserver.out.log`

삭제 전에 각 파일의 해석된 절대경로가 현재 worktree 내부인지, Git 추적 파일이 아닌지 확인한다. `.gitignore`에는 다음 규칙을 추가해 같은 로그가 다시 작업 목록에 나타나지 않게 한다.

```gitignore
.codex-dev-server*.log
.codex-devserver*.log
```

다음 항목은 삭제하지 않는다.

- `.dev.vars`: 로컬 API 키 설정
- `.wrangler/`: 로컬 D1 데이터
- `node_modules/`, `.vinext/`, `dist/`: 기존 무시 규칙이 적용되는 생성물
- D1 마이그레이션, 테스트 fixture, 완료된 설계서와 구현 계획

## 6. 로드맵 재구성

활성 ROADMAP에서 확률 보정, 자체 승부예측, 모델 학습, 자동 추천, 백테스트용 별도 데이터 모델과 PWA 오프라인 계획을 제거한다.

향후 작업은 다음 순서로 정리한다.

1. 비공개 웹 배포 준비
   - 배포 환경의 `API_FOOTBALL_KEY` 등록
   - 운영 D1 생성과 마이그레이션 적용
   - 로컬 저장 데이터 이전 여부 결정
   - 저장·삭제·동기화 API 접근 제한
2. 운영 안정성
   - API-Football·Betman 오류, 호출량과 지연 시간 확인
   - 동기화 실패와 D1 오류 확인
   - 백업·복구 기준 마련
3. 데이터 품질
   - 팀 별칭 변경 근거와 출처 기록
   - 팀 매칭 실패 행 점검 절차
4. 사용성
   - 모바일 접근성 점검
   - 저장·조회 오류 안내 개선

## 7. 변경 범위

### 변경 대상

- `.gitignore`
- `README.md`
- `docs/PRODUCT.md`
- `docs/PRODUCT-EVOLUTION.md` 신규 작성
- `docs/ROADMAP.md`
- `docs/HANDOFF.md`
- `docs/DECISIONS.md`
- 지정된 개발 서버 로그 4개

### 변경하지 않는 대상

- 제품 코드와 API 계약
- API-Football Predictions 화면 및 `/api/predictions`
- D1 스키마와 저장 데이터
- `.dev.vars`와 `.wrangler/`
- 완료된 `docs/superpowers/specs` 및 `docs/superpowers/plans`

## 8. 검증

- 개발 로그 4개가 제거되고 동일한 파일명이 다시 생성돼도 Git 상태에 나타나지 않아야 한다.
- 활성 문서의 제품 목적, 기능 범위와 비목표가 서로 일치해야 한다.
- 활성 ROADMAP에 자체 승부예측, 확률 보정, 백테스트 또는 PWA 오프라인 계획이 남지 않아야 한다.
- API-Football Predictions는 외부 참고정보로 일관되게 설명되고 현재 코드와 API는 유지되어야 한다.
- 완료된 설계서와 구현 계획의 원문은 변경되지 않아야 한다.
- `.dev.vars`, `.wrangler/`와 로컬 D1 파일이 보존되어야 한다.
- 전체 타입검사, Vinext 빌드, 단위·렌더링 테스트와 린트가 통과해야 한다.

## 9. 완료 기준

활성 문서만 읽어도 현재 제품이 무엇인지, 초기 구상에서 무엇이 바뀌었는지, 어떤 미래 계획을 명시적으로 폐기했는지 알 수 있어야 한다. 작업 트리에는 개발 서버 로그가 노출되지 않아야 하며, 제품 코드·API·로컬 저장 데이터에는 동작 변화가 없어야 한다.
